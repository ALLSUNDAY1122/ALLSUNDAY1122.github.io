# Repository-wide agent safety rules

- Windows Office COM session-ownership guard (2026-10-31): When creating or visually checking `.pptx`/`.docx`/`.xlsx` files on a Windows desktop, **do not launch COM automation against an interactive Office application, or call `Application.Quit()` / close other open documents, without explicit human approval**. PowerPoint is a multiuse/single-instance COM server: acquiring `PowerPoint.Application` can refer to the user's already-running application even when code uses `New-Object -ComObject`; do not assume a newly obtained COM object means a newly owned process. Prefer generating the file with a non-interactive library (e.g. `python-pptx`) and previewing through a truly isolated renderer or existing non-COM inspection; do not silently fall back to Office COM if a renderer is missing. If COM is indispensable, stop as `OFFICE_COM_SESSION_UNVERIFIED` / `HUMAN_REQUIRED` until the user has saved interactive work and approved the exact app/session operations. Never use `Quit()` on an application whose sole ownership is unproven; even `Presentations.Count` alone is not sufficient proof of ownership. Do not save/close unrelated user documents as a workaround. This is an agent instruction, not a technical isolation boundary; no Windows Office test was run. Microsoft documents PowerPoint's single-instance COM behavior and that `Application.Quit` exits the application (https://learn.microsoft.com/en-us/previous-versions/office/troubleshoot/office-developer/use-visual-c-automate-run-program-instance ; https://learn.microsoft.com/en-us/office/vba/api/powerpoint.application.quit). A 2026-10-31 Windows Claude user reported losing unsaved work after automated visual QA invoked `Quit()` on an existing PowerPoint session (https://github.com/anthropics/claude-code/issues/106370); exact product-wide prevalence is unverified. Rollback: remove only this bullet.

- Claude Code v2.1.316 security-boundary verification (2026-10-31): Before relying on a Windows PowerShell `PreToolUse`/permission hook as a fail-closed security barrier, or on `claude --restricted` to prevent uploads outside working directories, inspect the effective Claude Code version, hook command and permissions **read-only**. Anthropic's official v2.1.316 release fixes (a) exit-code-2 PowerShell hook blocks not being enforced when a command begins with a type cast, `param`, `using`, or an attribute, and (b) restricted sessions uploading outside working directories when a Read allow rule covered those paths (https://github.com/anthropics/claude-code/releases/tag/v2.1.316; https://code.claude.com/docs/en/hooks). On earlier or unverified versions, **do not assume either boundary works**; keep sensitive-file uploads and security-relevant unattended operations stopped as `CLAUDE_BOUNDARY_UNVERIFIED` until a harmless isolated denial test proves the effective behavior or a human approves a supported update. A release note does not prove the installed version or a successful local regression test. Do not weaken hooks/Read restrictions, alter credentials, or upgrade running workers automatically. Rollback: remove only this bullet.

- Claude Code hook-host liveness and fail-closed guard (2026-10-31): Before unattended multi-agent or security-sensitive Claude Code work, inspect the effective `PreToolUse` hooks, their timeouts, and host responsiveness **read-only**. Anthropic documents that timed-out `PreToolUse` command/HTTP hooks normally do not block the tool call; on Claude Code >=2.1.295, `onFailure: "block"` is the documented fail-closed setting for supported command/HTTP hooks (https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails). Do not assume this setting is present, effective on the installed version, or sufficient against a frozen Desktop host: a macOS user reported 600-second hook waits while six background agents kept making API calls, repeatedly missing five-minute caches (https://github.com/anthropics/claude-code/issues/106385). For security gates, require an isolated harmless deny/timeout test before trusting the hook; if the host stops answering, repeated 600-second hook waits occur, or the result cannot be independently verified, stop dependent unattended writes and classify `CLAUDE_HOOK_HOST_UNVERIFIED` / `HUMAN_REQUIRED`. Bound background-agent runtime and monitor progress and usage via independent, authorized read-only signals; never bypass the hook, force-stop ambiguous workers, or change global permissions/credentials automatically. The incident was reported on macOS, not reproduced on the user's Windows host; this instruction is not a technical watchdog. Rollback: remove only this bullet.

- Windows connected-desktop execution completion gate (2026-10-31): If a ChatGPT/Codex connected Windows command loses its execution handle, the exec-server transport disconnects, recovery times out, or an execution reports `Unknown process id`, `aborted by user`, or exit `-1` without authoritative terminal evidence, classify it as `EXECUTION_COMPLETION_UNVERIFIED`. Preserve the original handle, task/command scope, start time, and any non-sensitive receipts. Check the intended outcome **read-only** through an independent authorized source (for example process ID plus creation time, expected artifact/commit/CI state), without exposing secrets. A missing handle, UI cancellation, or disconnected transport is **not** proof that the process stopped or the side effect failed. Never blindly rerun, switch execution routes to evade policy, kill an ambiguous process, or start a duplicate worker. Resume only work independently shown to be unfinished; if completion cannot be established, stop dependent writes/push/deploy as `HUMAN_REQUIRED`. A retry requires evidence that the operation never started or an independently reviewed idempotent, duplicate-safe plan. This is an agent-level precaution, not a repair to the desktop transport (single-user report: https://github.com/openai/codex/issues/58376). Rollback: remove only this bullet.
- Windows linked-worktree cleanup prerequisite gate (2026-10-30): Before any `git worktree remove`, `git worktree prune`, or equivalent directory cleanup on Windows, check whether the candidate worktree contains NTFS junctions, symlinks, or other reparse points to shared virtual environments, dependency caches, or sibling worktrees. A planned detach/unlink step is a **hard prerequisite**, not a best-effort warning: verify its success AND independently inspect the candidate path read-only to establish that no link into shared resources remains; also verify the exact worktree identity, live session/lock state, and preserved evidence. If detachment was denied, failed, timed out, or cannot be verified, stop all dependent removal as `WORKTREE_LINK_DETACH_UNVERIFIED` / `HUMAN_REQUIRED`; never continue with `--force`, recursive deletion, an alternate shell, or an automatic cache rebuild. Do not assume that a successful unlink return code proves the target is isolated. Git documents that `worktree remove` removes a working tree and `--force` overrides cleanliness checks (https://git-scm.com/docs/git-worktree); Microsoft documents read-only reparse-point inspection (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-reparsepoint). A Windows Claude Code 2.1.314 user reported proceeding after a blocked junction detach and subsequently finding a shared Python venv cache empty across eight worktrees (https://github.com/anthropics/claude-code/issues/106243); the exact deletion mechanism and Git causality are **unverified**. This adds a failure-propagation gate to existing no-shared-path cleanup rules, not a permission to remove worktrees automatically. Roll back by removing only this bullet.

- Codex Streamable HTTP MCP query-secret preflight (2026-10-30): Before adding or using an HTTP MCP endpoint in Codex/Claude/CI, inspect its URL **locally/read-only without printing secret values**. Do not place access tokens, API keys, signed credentials, or other secrets in URL query parameters or fragments; the MCP HTTP authorization specification requires bearer access tokens in the `Authorization` header and forbids access tokens in the query string (https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization). A Codex 2026-10-30 source-based report (https://github.com/openai/codex/issues/58301) and inspected upstream code show that `tools/list` retry warnings may include an unsanitized transport-error URL after a transient failure; this is **not** a maintainer-confirmed end-to-end Codex reproduction. Prefer an officially supported header/OAuth mechanism; do not invent an unsupported auth mode or migrate a live endpoint automatically. If the current MCP endpoint requires query-string credentials or cannot be checked without revealing them, stop dependent setup as `MCP_QUERY_SECRET_UNVERIFIED` / `HUMAN_REQUIRED`. Treat local WARN logs and CI artifacts as potentially sensitive; redact complete query/fragment and nested URL-bearing error fields before sharing, without dumping originals. Do not change/rotate credentials, delete logs, modify production MCP connections, or weaken logging/security checks autonomously. This is an agent preflight, **not** a runtime log-redaction fix. Roll back by removing only this bullet.

- Windows Codex Computer Use same-app multi-window target-integrity guard (2026-10-30): When using Windows Codex Computer Use (`sky.set_value`, click, type, or similar UI automation) with **two or more top-level windows of the same app**, a fresh `get_window_state`/element index and window-local `focused_element` are **not sufficient evidence** that the intended document will receive the write. A Windows 11 / Codex Desktop 26.1027.3384.0 user observed one `set_value` addressed to Notepad Window B changing Window A while B remained empty (single synthetic-document observation; native cause and general reproducibility unconfirmed: https://github.com/openai/codex/issues/58315). Before any consequential GUI write, verify the exact top-level window identity, target document/title and current content via read-only observation, and where possible independently establish foreground/target identity. If ambiguity remains, stop with `GUI_WINDOW_TARGET_UNVERIFIED` / `HUMAN_REQUIRED` rather than retrying or relying on the return status. Prefer a user-authorized exact-path file/API operation over ambiguous GUI routing when appropriate. After a permitted write, independently read back the intended target **and check that other open same-app documents did not change**; preserve evidence and stop on mismatch. Never use real private data to reproduce, weaken UI permissions, or treat this AGENTS.md instruction as an OS-enforced guard.
- Windows Codex/ChatGPT Work local-browser host-mode preflight (2026-10-30): If a **Codex-created local session** (including one selected from iPhone as Codex > local PC) suddenly reports `Local browser use is disabled in Work settings` or returns an empty browser inventory, do **not** infer that the user's browser permissions were disabled. First check read-only the desktop host's active ChatGPT-versus-Codex experience, the session's origin/kind, and whether the failure occurs only while continuing it as Work. In a documented Windows report, browser discovery failed with the PC host in ChatGPT/Work mode and recovered after the **user** switched that host to Codex mode, without changing permissions (https://github.com/openai/codex/issues/58295; single user report, not a general product guarantee). Preserve the session and task state; do not repeatedly toggle permissions, request credentials, alter sandbox/browser safety checks, or change the desktop mode without the user's authorization. If host mode cannot be verified or the mismatch persists, stop dependent browser actions as `WORK_BROWSER_HOST_MODE_UNVERIFIED` / `HUMAN_REQUIRED`; use only an already approved alternative. This is an agent diagnostic, not a runtime fix. Roll back by removing only this bullet.

- Claude Cloud setup-script failure gate (2026-10-30): Anthropic's official Claude Code v2.1.314 release changed cloud sessions started from web, desktop, or mobile to **start even if the setup script exits with an error** (https://github.com/anthropics/claude-code/releases/tag/v2.1.314). For any cloud session that depends on a setup script, successful session creation is **not** proof that dependencies, build tools, or project initialization succeeded. Before mutating source, running CI/builds, or declaring success, read the available setup result and check expected non-secret dependency/artifact readiness; if failure or unverifiable, stop dependent side effects with `CLAUDE_CLOUD_SETUP_UNVERIFIED` / `HUMAN_REQUIRED`. Do not silently rerun potentially mutating setup, change secrets, disable checks, or claim an unverified environment is ready. This is an agent-level preflight, not a platform-enforced guard; unaffected sessions without setup scripts need no change. Roll back by removing only this bullet.

- Claude Code v2.1.314 scoped file-write guard preflight (2026-10-30): Anthropic's official v2.1.314 release adds `permissions.blockWritesOutsideWorkingDirectories`, which makes built-in `Write`, `Edit`, and `NotebookEdit` reject paths outside the effective working directories in every permission mode (https://github.com/anthropics/claude-code/releases/tag/v2.1.314). Before recommending it for unattended Windows/Claude workers, check the **actual** Claude Code engine version (Desktop's bundled engine can differ), the intended primary/additional working directories, and existing `.claude/settings.json` / `.claude/settings.local.json` / user settings. Test only in a disposable, non-production project with an in-scope and out-of-scope file; verify denial and that normal builds still work. Do not silently set this option globally or in a shared repo when workers legitimately write to sibling directories, and do not assume it restricts Bash/PowerShell, arbitrary subprocesses, MCP, GitHub/Notion connectors, or the OS filesystem: it is a built-in file-tool guard, **not** a sandbox. If version, scope, or effect is unverified, mark `CLAUDE_WRITE_SCOPE_UNVERIFIED` / `HUMAN_REQUIRED` before expanding unattended writes. The official all-settings reference had not yet documented this new key when checked on 2026-10-30 (https://code.claude.com/docs/en/settings-reference); require an effective-settings check and actual harmless test before deployment. Roll back any approved future setting by removing only this key and restarting the session.

- Windows ChatGPT Work Git ownership preflight (2026-10-30): If a local Git read fails with `fatal: detected dubious ownership` under a sandbox identity such as `CodexSandboxOffline`, do **not** treat this as a Git defect or disable its ownership protection. First inspect read-only the effective process identity, the exact canonical repository path, its owner, and whether the user explicitly trusts that repository. For a **confirmed user-owned, trusted, single repository**, a one-command, repo-specific diagnostic may use `git --no-optional-locks -c safe.directory=<exact-absolute-repo-path> -C <exact-repo-path> rev-parse --show-toplevel`; compare the returned root with the expected path, and only then consider similarly scoped **read-only** `rev-parse` / `status` / `diff` checks. Never use `safe.directory=*`, a parent wildcard, persistent `git config --global/--system`, owner/ACL changes, sandbox disablement, or Git writes as an automatic workaround. If ownership, path resolution, or trust is uncertain, stop with `WORK_GIT_OWNERSHIP_UNVERIFIED` / `HUMAN_REQUIRED`. This is a limited diagnostic, not a Git security fix; successful reads do not establish write safety or absence of filesystem side effects. Source: https://github.com/openai/codex/issues/58222 (single Windows Work report, 2026-10-30) and Git's official `safe.directory` documentation: https://git-scm.com/docs/git-config#Documentation/git-config.txt-safedirectory .

- Claude Code project-hook scope isolation (2026-10-30): Before installing, modifying, or enabling a hook intended for one project, inspect **read-only** the effective settings scope and any hook configuration lookup that walks parent directories. Anthropic documents that `%USERPROFILE%\.claude\settings.json` applies to **every** project on the machine, while a project's `.claude/settings.json` or `.claude/settings.local.json` is scoped to that project (https://code.claude.com/docs/en/settings). Do not silently place project-only hooks in user-wide settings, a shared parent `.claude/` directory, or a globally referenced script/config; check the resolved paths and which sibling projects or sessions would inherit them. Require explicit human approval for any user-wide, shared-parent, or cross-project hook installation or change; if the effective scope cannot be verified, stop as `CLAUDE_HOOK_SCOPE_UNVERIFIED` / `HUMAN_REQUIRED`. Do not automatically remove, relocate, or disable existing hooks while investigating. A Windows Claude user reported 18 project-specific hooks installed at user scope and a shared parent, causing unrelated projects to inherit them (https://github.com/anthropics/claude-code/issues/106075); this is a single user report, not evidence of a universal product bug or an OS-enforced isolation boundary.

Applies to work in this repository, including parallel agents and Git worktrees. More specific project instructions remain in force.

Do not print the original URL to diagnose it or publish a pre-redaction excerpt. If a signed URL may already have escaped, stop automated sharing as `CODEX_PLUGIN_SIGNED_URL_UNVERIFIED` / `HUMAN_REQUIRED`; token rotation or credential changes require human approval. - Playwright MCP mutating-tool annotation preflight (2026-10-30): Treat `test_run`, `test_debug`, `generator_setup_page`, `planner_setup_page`, `generator_write_test`, and `planner_save_plan` as potentially executing code or writing workspace files, **even if MCP advertises `readOnlyHint: true`**. Before an unattended call, review the tool implementation, target workspace, test side effects, and task authorization independently; do not let `readOnlyHint` bypass the existing human-approval gate for writes, code execution, or external effects. If effects cannot be verified, stop with `PLAYWRIGHT_MCP_EFFECT_UNVERIFIED` / `HUMAN_REQUIRED`. - Claude Code skill pre-execution shell guard (2026-10-29): Before invoking a newly installed, updated, or unreviewed local/project/plugin/add-dir skill or custom command in a Windows/Claude worker, inspect its `SKILL.md` or command Markdown **as inert text**, including frontmatter `allowed-tools`, hooks, inline whitespace-prefixed `!` backtick-command substitutions, and fenced `!` shell blocks. Official Claude Code docs state that these substitutions can execute Bash/PowerShell **before the skill body reaches the model**, even when an author intended them as examples; an October 29 report identifies such examples in `plugin-dev:command-development` v0.2.0. Do not invoke the skill to test whether it is safe. If any pre-execution command is unreviewed, ambiguous, or outside the task's explicit allowlist, stop with `CLAUDE_SKILL_SHELL_UNVERIFIED` / `HUMAN_REQUIRED`. The documented `disableSkillShellExecution: true` setting disables these substitutions for user/project/plugin/add-dir skills and custom commands, but **not bundled or managed skills**; account-synced skills are handled separately. Never change persistent settings, enable plugins, or loosen permission rules autonomously. This is an agent preflight, **not** an enforced execution boundary. Sources: https://code.claude.com/docs/en/skills#inject-dynamic-context ; https://github.com/anthropics/claude-code/issues/105911 .

- Claude Code path-deny rule verification (2026-10-29): Before relying on Claude Code `permissions.deny` to protect private files in an unattended Windows/Claude worker, inspect the effective rules read-only. Official Claude Code documentation states that scoped `Glob(path)`, `Write(path)`, and `NotebookEdit(path)` rules are accepted but **never match**; use `Read(path)` for reads and `Edit(path)` for writes, or deny the entire tool by bare name when appropriate. Verify rule anchoring (`~/`, `//` for absolute, `/` relative to the settings source), including Windows drive normalization, and do not infer protection from a successful config parse. A user report also alleges a `Read`-rule mismatch in Claude Code 2.1.112 on macOS, but the cause and applicability to current Windows builds are unverified (https://github.com/anthropics/claude-code/issues/105862). For truly sensitive files, enforce an independent OS sandbox/ACL boundary; Claude Code's own docs say path rules do not constrain arbitrary subprocesses. If effective scope is unknown, block sensitive reads/writes as `CLAUDE_PATH_DENY_UNVERIFIED` / `HUMAN_REQUIRED`; do not read secrets to test a deny rule, relax permissions, or alter credentials. Sources: https://code.claude.com/docs/en/permissions#writepath-notebookeditpath-and-globpath-rules-never-match and https://code.claude.com/docs/en/permissions#what-read-and-edit-rules-cover. This is a policy guard, not an implemented OS access control.


- Codex MCP OAuth IPv6 callback bind preflight (2026-10-30): Before an unattended Codex/Windows worker initiates OAuth for a remote MCP server with a custom callback/redirect URI, inspect the configured URI and effective listener address **read-only**. Upstream `codex-rs/rmcp-client/src/perform_oauth_login.rs` currently matches `Url::host_str()` against `"::1"` but Rust `url` serializes an IPv6 loopback host as `"[::1]"`; this can select `0.0.0.0` for a callback URL such as `http://[::1]:PORT/callback` instead of loopback. Treat an IPv6 callback, a wildcard bind, or an unverified listener as `CODEX_MCP_OAUTH_BIND_UNVERIFIED` / `HUMAN_REQUIRED` before starting OAuth; prefer an explicitly verified IPv4 loopback callback (`127.0.0.1`) only when supported by the provider and reviewed by the human. Do not start a probe OAuth flow, open a firewall port, change OAuth redirect registration, reconnect accounts, change credentials, or weaken authentication automatically. This is distinct from the local MCP **server** listener guard: it covers the transient OAuth callback listener. The upstream issue is an unconfirmed user report, but the conditional code path is independently visible; affected installed versions and actual Windows exposure are unverified. Sources: https://github.com/openai/codex/issues/58115 ; https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/perform_oauth_login.rs ; https://docs.rs/url/latest/url/enum.Host.html . This is an agent preflight, not a runtime network control.
- Local HTTP MCP listener exposure guard (2026-10-29): Before starting an MCP server over HTTP/SSE on a Windows workstation or CI host, verify the effective listening address using a read-only check. Prefer stdio or explicit loopback binding (`127.0.0.1` / `::1`) for local-only tools. In `@modelcontextprotocol/server-everything` 2.0.1, the HTTP transports call `app.listen(port)` without a host, which can bind all interfaces; its browser Origin restriction does not protect against non-browser LAN clients (https://github.com/modelcontextprotocol/servers/issues/5371 ; https://github.com/modelcontextprotocol/servers/blob/main/src/everything/transports/listen.ts). Do not treat a localhost URL or Origin/CORS filtering as proof of loopback binding. If the bind address cannot be verified, stop launching/exposing that server as `LOCAL_MCP_BIND_UNVERIFIED` / `HUMAN_REQUIRED`; do not open firewall ports, change network visibility, or terminate running processes autonomously. This is a preventive instruction, not a runtime firewall or evidence that the user's current machine is exposed.
- Claude Code non-interactive untrusted-checkout hook preflight (2026-10-29): Before running `claude -p` or a Claude Agent SDK session in a newly cloned, third-party, or otherwise untrusted repository, **read-only** inspect its `.claude/settings.json`, applicable project/local hook declarations, and any enabled plugin/skill hooks. Anthropic's official Hooks reference states that `-p`/SDK sessions do not show the workspace-trust dialog and treat the folder as trusted, so repository-supplied hooks may execute with the current user's permissions (https://code.claude.com/docs/en/hooks#workspace-trust). Do not run unreviewed hooks or silently change persistent hook/permission settings. Use a separately approved isolated invocation (`--bare` or an explicitly reviewed per-run `--settings '{"disableAllHooks":true}'` where applicable), or stop with `UNTRUSTED_HOOKS_UNVERIFIED` / `HUMAN_REQUIRED`; managed hooks and other execution paths must be checked independently. This is a documented trust behavior, not a newly confirmed exploit or an OS sandbox.
- Claude Code local connector-scope preflight (2026-10-29): A `claude.ai` subscription login can automatically make account-connected MCP services available to Claude Code terminal, VS Code, JetBrains, and Agent SDK sessions, independently of the local OS user's or `gh` CLI's permissions. Before an unattended `claude -p`/SDK run or an agent task with external read/write effects, verify the effective connector/tool inventory against the task's explicit allowlist using an interactive **read-only** `/mcp` inspection or a verified equivalent; never assume the local account or a restricted worktree limits connector authority. If unexpected connectors are available or the effective inventory cannot be verified, stop external side effects as `CLAUDE_CONNECTOR_SCOPE_UNVERIFIED` / `HUMAN_REQUIRED`. For sessions that fetch connectors themselves, the documented `disableClaudeAiConnectors: true`, `ENABLE_CLAUDEAI_MCP_SERVERS=false`, or per-server deny controls are possible *human-reviewed* containment options; do not silently change account connections, credentials, or persistent settings. These switches **do not apply** to cloud-host-delivered or Claude Desktop local/SSH in-process connectors: verify host controls separately; Desktop users may need to disconnect a connector in claude.ai, which requires human approval. Do not expose connector identities, tokens, or private resource names in public logs. - Repository administration and user-intent gate (2026-10-28): Do not archive/unarchive a repository, change its visibility or ownership, alter default-branch/branch-protection rules, or disable workflows based on inferred intent, conversational assent, or a model-suggested action. Wording such as "let me do it", "I will do it", or "I will handle it" reserves execution to the human, even if adjacent words describe an operation. For repository-wide availability, access, or publication changes, require an unambiguous direct user instruction naming the repository and exact operation; then stop at `HUMAN_REQUIRED` if the action changes external visibility, access, or existing production behavior. Do not use `--yes` or equivalent to bypass a required human confirmation. A single Claude Code user reported an unintended `gh repo archive` after saying "let me do it" (https://github.com/anthropics/claude-code/issues/105600); this is a precaution, not a verified general product defect or an enforcement boundary.
- Windows Claude Code VS Code session-reload single-owner guard (2026-10-28): After `Developer: Reload Window`, extension recovery, or a session `--resume`, do not assume that the visible tab is the only process running that session. Before allowing any scheduled job, GitHub write, notification, or other side-effectful task to resume, check **read-only** whether two live `claude.exe` processes share the same session ID (`--resume`), using PID **and creation time** and redacting other command-line arguments; cross-check the session's task/Queue state and completed effects. A single Windows 11 / Claude Code extension 2.1.312 report observed a hidden and visible process both running the same session-only cron jobs and appending to the same `.jsonl` transcript (https://github.com/anthropics/claude-code/issues/105666). If ownership cannot be established, mark `SESSION_OWNER_UNVERIFIED`, block any duplicate side effects, and escalate `HUMAN_REQUIRED`; do not automatically terminate a process, delete transcripts, replay a task, or send a message. This is an agent-level precaution, not a VS Code/Claude process-lock fix.
- GitHub MCP pull-request merge-state verification (2026-10-29): When `github-mcp-server` `list_pull_requests` returns a closed PR with `merged: false` or an absent `merged` field, do **not** infer that the PR was closed unmerged. GitHub's REST **list** response may omit `merged`; GitHub MCP Server <= v2.0.3 can convert the missing field to false (https://github.com/github/github-mcp-server/issues/3467). Fix PR https://github.com/github/github-mcp-server/pull/3468 merged on 2026-10-28 but was not included in the latest verified v2.0.3 release. For PR status used in Worker Queue, integration, release, branch cleanup, or audit, read `merged_at` and independently verify the **single PR detail** (`GET /repos/{owner}/{repo}/pulls/{number}`), or GitHub's dedicated merge-status endpoint, before classifying merged versus closed-unmerged; also record `merge_commit_sha` and expected base/head as appropriate. If list and detail conflict or cannot be read, mark `PR_MERGE_STATE_UNVERIFIED` and stop side effects with `HUMAN_REQUIRED`. Do not update the MCP server or alter PR/branch state automatically. This is a read-only verification rule, not a fix for the server.
- PR-branch pre-push merged-state freshness gate (2026-10-30): For an agent/Worker continuing work on a branch associated with an existing PR, do not assume that a queued `pull_request.closed` notification, the last-known open PR state, a successful `git push`, or an editable PR title/body means the PR is still open. A Claude Cloud session pushed a follow-up commit after its PR had been merged, because the merge notification was delivered only at the next turn boundary (~5 minutes later; single reported incident: https://github.com/anthropics/claude-code/issues/106190).
