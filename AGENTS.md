# Repository-wide agent safety rules

Applies to work in this repository, including parallel agents and Git worktrees. More specific project instructions remain in force.

- A Git worktree separates checkouts; it is **not** an operating-system filesystem sandbox. Do not assume it prevents access to the user's home directory, sibling projects, credentials, or other worktrees. On native Windows, Claude Code's Bash/PowerShell commands run without its OS sandbox (the documented sandbox requires WSL2).
- Before running **agent-generated** tests, shell scripts, package lifecycle scripts, or cleanup jobs, inspect the commands and fixtures for shell evaluation/interpolation (`sh -c`, `bash -c`, `cmd /c`, PowerShell evaluation), recursive deletion, absolute/home paths, and symlink/junction traversal. A test runner can execute a destructive payload indirectly.
- Injection and cleanup tests must use harmless marker files in a dedicated disposable test directory, not real destructive commands as test input. Keep destructive mocks active through `finally`, teardown, and finalizers. Never run an unreviewed destructive test against the real checkout or home directory.
- Before any actual cleanup, resolve the target's canonical path and verify that it is strictly inside an explicitly disposable directory. Refuse the home directory, repository root, `.git`, other worktrees, shared directories, unexpected symlinks/junctions, and paths that cannot be proven safe. If uncertain, stop with `HUMAN_REQUIRED`.
- Hard links can share one file's contents across different paths even when both paths pass canonical-path checks. Before an in-place overwrite or edit of an existing file in an untrusted/disposable tree, inspect its hard-link count when available (`nlink` or a verified `get_file_info` `hardLinks` field). If it exceeds 1, or cannot be checked and an outside file could be affected, do not perform the in-place mutation; stop with `HUMAN_REQUIRED`. Symlink/junction checks and worktree separation do not detect this aliasing. Do not assume an unreleased MCP field is installed.
- On native Windows, `@modelcontextprotocol/server-filesystem` 2.0.1 `allowedDirectories` is **not a complete write-containment boundary**: a concurrent process may swap a parent directory for a junction after path validation, redirecting `write_file`, `edit_file`, `create_directory`, or a `move_file` destination. The official v2.1.0 release explicitly states the fix is only partial on Windows. When another process can modify intermediate directories, do not use these MCP write operations on untrusted/mutable trees; prefer a trusted, controlled workspace or a repository-scoped API, and stop with `HUMAN_REQUIRED` if containment cannot be established. Canonical-path checks, symlink/junction checks, and hard-link counts do not eliminate this race. This agent instruction is not a server patch or OS security boundary.
- Do not autonomously create, install, register, enable, or persist custom approval-interception plugins, permission hooks, policy wrappers, background services, or equivalent authorization controls as a side effect of a broader deployment or "security hardening" request. Such controls can change the effective approval boundary independently of the native approval mode. Before any persistent change, document the component, scope, host, lifecycle, interaction with native approvals, rollback, and exact user authorization; otherwise stop with `HUMAN_REQUIRED`. Do not silently remove or disable an existing control either. This applies to third-party agents and local scripts as well as Codex/Claude plugins; the reported Hermes incident is not evidence of a Codex product exploit.
- Codex marketplace host allowlists require a runtime version check before any approved marketplace-source registration or fetch. The official Codex CLI 0.165.0 release fixed a URL parser/Git host mismatch: a literal backslash in HTTP(S) URL userinfo could satisfy an allowed-host pattern while Git/libcurl connected to a different host. Check the **actual executing** Codex version (`codex --version` for CLI; desktop's bundled version may differ), require 0.165.0 or a verified backport for marketplace URL host validation, and independently confirm the intended canonical Git origin. If version, source host, or effective runtime cannot be verified, do not fetch/install; report `HUMAN_REQUIRED`. This does **not** authorize plugin installation without the existing explicit approval. Official evidence: https://github.com/openai/codex/releases/tag/rust-v0.165.0 and https://github.com/openai/codex/pull/56263 .
- On native Windows, never launch recursive cleanup through a nested shell or constructed command string (for example PowerShell invoking `cmd /c rmdir /s /q` for `node_modules`). Shell quoting can change the effective target even if the intended path was checked beforehand. Do not automatically delete a project's `node_modules` to fix dependency conflicts. If deletion is genuinely necessary, require `HUMAN_REQUIRED` for the exact target and use a separately reviewed, non-shell filesystem operation with canonical-path and ancestor/drive-root rejection; a failed or partial cleanup must never trigger a broader retry. A single-user React Native/Expo incident reported deletion outside the project; the upstream root cause is not independently established (https://github.com/openai/codex/issues/57530; https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/rmdir).
- Supabase CLI `secrets set` (observed in versions 2.118.0–2.122.0) can load `[edge_runtime.secrets]` from the **process working directory**, ignoring `--workdir` for that configuration source. Do not treat `--workdir` as isolation for remote secret updates or run `supabase secrets set` autonomously across project directories. Before any proposed remote secret write, independently verify the effective working directory, `supabase/config.toml` (including remote overrides), the destination project ref, and the names of secrets that would be submitted; never print secret values. Because remote secret changes require explicit approval, stop at `HUMAN_REQUIRED` with a redacted plan. Prefer a separately reviewed, project-local working directory rather than relying on `--workdir`; do not use a live project to reproduce the bug. Upstream issue and implementation: https://github.com/supabase/cli/issues/7354 and https://github.com/supabase/cli/blob/develop/apps/cli/src/commands/secrets/set/set.handler.ts . This is a precaution, not a CLI patch.
- Do not disable sandboxing, weaken OS permissions, expose secrets, or change production deletion behavior to make a test pass. Prefer static review and non-destructive checks; a genuine destructive integration test requires a separately approved isolated environment.
- These instructions guide agents but are **not an enforcement boundary**. Retain OS-level restrictions, independent verification, and the existing human-approval gates for high-impact operations.
