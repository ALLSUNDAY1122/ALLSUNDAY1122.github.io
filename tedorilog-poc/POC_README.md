# POC_README｜手取りログ Phase A PoC（給与明細 PDF・OCR 取込）

本番実装ではなく、**使い捨ての検証用PoC**。
目的は「給与明細を短時間で下書き化し、ユーザーが安全に確認・修正できるか」を判定すること。
100%の自動抽出は目標にしていない。

判定結果は [POC_DECISION.md](./POC_DECISION.md)、数値は [POC_RESULTS.md](./POC_RESULTS.md)、
失敗の分類と残課題は [POC_FAILURES.md](./POC_FAILURES.md)。

## 守っている制約

- 明細の画像・PDF・認識結果を**外部へ一切送信しない**（AI API、OCR APIを含む）。解析はすべてローカル。
- 実在の給与明細・個人情報は**一切扱わない**。固定コーパスは全て合成データ。
- 認識値を**ユーザー確認なしで確定保存しない**（`engine/save_guard.js` でコードとして保証）。
- 仕様外の機能は追加しない（課金・iCloud・本番UIの作り込みは対象外）。

## 実行方法

```bash
cd tedorilog-poc
npm install          # pdf.js（PDFテキスト抽出）のみ。実行時に外部通信はしない
npm test             # 自動テスト（36件）
npm run eval         # 固定コーパス10形式の評価（--md で POC_RESULTS.md を再生成）
node eval/robustness.mjs 200 0.5   # 劣化注入テスト（OCRがもっと悪い環境の想定）
```

PoC UI（画面A/B/C）は静的ページ。ローカルで開く場合:

```bash
python3 -m http.server 8000   # リポジトリのルートで実行
# http://localhost:8000/tedorilog-poc/ を開く
```

- **テキスト埋込PDF**はブラウザ上で実際に解析する（同梱のpdf.jsを使用、CDNは使わない）。
- **画像・スキャンPDF**の文字認識は本番では端末内のApple Visionを使う想定。
  ブラウザPoCにはOCRエンジンを積まないため、ローカルOCR済みの固定コーパスを再生して挙動を確認する。

固定コーパスを作り直す場合（Tesseract日本語が必要。生成物はコミット済みなので通常は不要）:

```bash
sudo apt-get install -y tesseract-ocr tesseract-ocr-jpn
bash tools/build_corpus.sh
```

## 構成

```
engine/            解析エンジン（ブラウザ・Node・評価ハーネスで共有）
  normalize.js       文字/金額の正規化。表記ゆれ・OCRゆれの吸収
  lexicon.js         9項目＋合計行の表記ゆれ辞書
  layout.js          行・列の再構成（トークン連結、傾き推定、金額列検出）
  extract.js         候補生成・割当・検算・状態判定の中核
  digit_repair.js    合計整合を使ったOCR桁誤りの補正（曖昧なら補正しない）
  save_guard.js      ユーザー確認なしの保存を禁止する層
  pdf_tokens.js      ブラウザ側のPDFテキスト抽出（pdf.js）
tools/             固定コーパス生成・OCR・調査用ツール（開発時のみ使用）
fixtures/          合成明細（PDF/PNG）、抽出済みトークン、正解値
eval/              評価ハーネスと結果（results.json / robustness.json）
test/              自動テスト
index.html app.js styles.css   PoC UI（画面A/B/C）
vendor/pdfjs/      同梱pdf.js（外部CDNを使わないため）
```

## 処理の流れ

```
入力
 ├─ PDF ──→ pdf.js でテキスト抽出 ──┐   テキストが取れない場合はOCRへ
 └─ 画像 ─→ 端末内OCR ─────────────┤   （本番: Apple Vision / 検証環境: ローカルTesseract）
                                    ↓
                    位置つきトークン列 {text, x, y, w, h, conf}
                                    ↓
   layout.js  トークン連結 → 傾き推定 → 行クラスタ → 金額列検出
                                    ↓
   lexicon.js 項目名の判定（表記ゆれ・1文字までのOCR誤りを許容）
                                    ↓
   extract.js 候補の対応付け（同一行の右隣 → 行内の境界内 → 列ヘッダの真下）
                                    ↓
   digit_repair.js 支給合計・控除合計・差引の整合で桁誤りを検出／補正（曖昧なら見送り）
                                    ↓
   状態判定  確定候補 / 要確認 / 未検出   ← 検算の裏付けが無ければ確定候補にしない
                                    ↓
   画面B で確認・修正 → save_guard.js → 保存
```

## 解析の考え方（要点）

1. **金額の対応付けは近さだけで決めない。** 同一行でラベルの右側にある金額を優先し、
   同じ行に次のラベルがある場合はそこを境界にする（2段組で隣の列の金額を取らないため）。
   列ヘッダ型（ラベルの真下に金額）は、ラベルと金額が相互に最近傍のときだけ採用する。
2. **合計は検算に使う。** 「支給合計 = 基本給＋残業＋その他」「控除合計 = 各控除」
   「差引 = 支給合計 − 控除合計」。まず合計同士の関係で基準となる合計を確かめ、
   その後で各項目を検算する（合計が誤読されたまま項目を直すと、正しい項目を壊すため）。
3. **OCRの桁誤りは合計から補正できるが、曖昧なら補正しない。**
   同じくらい尤もらしい直し方が複数ある場合は、正しい値を壊す危険の方が大きいので何もしない。
   補正した値は必ず「要確認」で提示し、元の読み取り値も別候補として残す。
4. **確定候補にするには検算の裏付けが要る。** 裏付けの無い項目は、値が取れていても「要確認」。
   PDF直接抽出でも同じ扱いにしている（埋め込みフォントの不備で文字が化ける明細があるため）。
5. **残業関連とその他手当は互いに振り替えても支給合計が変わらない。**
   このため、項目名が完全一致していない手当を含む場合は確定候補にしない。

## 評価の指標

`eval/run_eval.mjs` が明細ごとに記録する。

| 指標 | 定義 |
| --- | --- |
| 正しく提示 | 9項目のうち、正解と完全一致する値を候補として提示できた数 |
| 誤り | 候補は出したが値が正解と違う数 |
| 未検出 | 候補を出せなかった数 |
| 誤確定 | 誤った値を「確定候補」として出した数（**0でなければPASSにしない**） |
| 修正操作 | 誤りの修正＋未検出の手入力の想定回数 |
| 確認タップ | 値は正しいが「要確認」で、確認だけが必要な項目数 |

## 検証環境と本番の差

| | 本番（iOS想定） | このPoCの検証環境 |
| --- | --- | --- |
| PDFテキスト抽出 | PDFKit | pdf.js（同じトークン形式） |
| 画像の文字認識 | Apple Vision（端末内） | Tesseract 日本語（ローカル実行） |
| 実行環境 | iPhone | Linux コンテナ / ブラウザ |

いずれも外部APIへは送信しない。Tesseractは日本語の項目名でVisionより弱いため、
本PoCではOCR前処理（拡大・影の平坦化）と数字領域の再認識を明示的に行っている。
